# Testing

> [!IMPORTANT]
> **E2E tests on production:** the happy path, sad path and admin and console journey suites can run against the live
> apps, driven by Playwright in your own browser. The steps, the commands and what to install are in
> **[On production, from your own machine](#on-production-from-your-own-machine)**. A run changes production's data
> and calls live Gemini: run it on the maintainer's yes only.

How every test in the repository is run, what each one proves, and which journeys to cover. There are two kinds:

- **The gates** run on every pull request in CI, and before a change ships. They are fast and need no browser.
- **The suites** (a11y, e2e, parity, live, journey) take minutes and real browsers, and some call live Gemini. They run
  **only when the maintainer asks for them** (SC-55): never as a routine step of a design, a port or a ticket. A
  project hook (`.claude/hooks/ask-before-suites.sh`) turns any attempt into a permission prompt, as a backstop.

Commands are from the repository root unless a line starts with `cd`. Setting the machine up is in
[README.md](README.md).

## The gates

What CI (`.github/workflows/ci.yml`) runs on every pull request to `main`, with a gitleaks secret scan and one
production build of every app.

**Frontend** (`frontend/`): ESLint and Prettier; `svelte-check` in every package; then Vitest in every package, after
the seed and icons checks (`seed:check`, `icons:check` fail when design3 changed and `corepack pnpm seed` or
`corepack pnpm icons` was not run). Vitest covers:

- core's components and the workspace app's screens, with golden texts of every role's screens at every stage;
- the drift tests that keep ported CSS verbatim and every app's `app.html` one file;
- the stub's journeys held to design3's `flow.js`, `money.js` and `ledger.js` at every stage;
- the workspace app's live source, in jsdom, on what backend-api really answered at five moments of the journey
  (`frontend/workspace/tests/live/fixtures/`, regenerated by `backend-api/scripts/live-fixtures.sh` after a change to
  the workspace routes);
- the guided demo's story held to design3's, line by line, station by station and beat by beat.

**backend-api:** ruff, then pytest against `smart_clearance_test`, migrated from scratch each run, with a fake
Firebase that never reaches Google. `backend-api/scripts/test.sh` passes its arguments to pytest
(`scripts/test.sh -k ledger -q`). The local test database is shared by every session on the machine, so run one suite
at a time.

**agents:** ruff, then about 200 pytest tests with no network and no live model: the stub tier's recordings,
backend-api as a recording mock, BigQuery and Cloud Storage fakes, every pipeline's trajectory, the reserve never
reaching a model, and the PDFs (WeasyPrint's render is skipped where Pango is not installed).

**infra:** `terraform fmt` and `validate` on both roots, the scripts' syntax and shellcheck. No plan: that needs
credentials and is read in full by a person before any apply.

## The browser suites: a11y, e2e and parity

### Before running

- **Browsers**, once: `cd frontend && corepack pnpm exec playwright install chromium webkit firefox`.
- **`PUBLIC_API_BASE` empty.** These suites run on the in-browser mocks and stubs, even while an app's `.env.local`
  points at an API. Prefix every command with `PUBLIC_API_BASE=`.
- **A build.** Each suite builds its app first and serves the build on its own preview port (a11y and e2e: admin
  4174, console 4177, workspace 4181, demo 4183; parity: 4175, 4178, 4182, 4184). The dev servers need not run, but
  a server left on one of those ports stops the suite from starting.
- **design3 built**, for parity: run `cd design3 && ./build.sh` if a `.jsx` changed. Parity serves design3 itself on
  :8790 (`frontend/testing/design3-server.py`).
- **Firefox** cannot start in a sandboxed shell (Claude Code's); its smoke run fails there and passes on a normal
  machine. Say so rather than treat it as a regression.
- **A long timeout**, 10 minutes, for each app's a11y run. Run the apps one at a time.

### a11y

```bash
cd frontend
PUBLIC_API_BASE= corepack pnpm test:a11y              # every app, one after another
PUBLIC_API_BASE= corepack pnpm test:a11y:workspace    # one app: :admin, :console, :workspace, :demo
```

On each app's production build (the real UI; the `/ds` design-system route is never scanned): axe-core's WCAG 2.2 AA
rules on every landing-page section, every console screen, tab, sheet, menu, alert and toast, every role's screen in
the workspace app, and every station of the guided demo beat by beat, in five projects (desktop light and dark, tablet,
phone light and dark). Then the keyboard specs (sign-ins, sheets that take, keep and return focus, menu buttons, the
demo's keys and route map) and the motion spec, which fails on any animation that never ends.

Last comes the **coverage check**: each scan records the core components on screen, and the run fails if an app uses a
core component no scan reached. A new component needs its selector in `COMPONENTS`
(`frontend/testing/src/a11y.ts`); a new screen or state needs a scan that reaches it. An app names the screens it never
shows in its `package.json` (`a11yCoverage.unreached`). Findings land in each app's `test-results/a11y/`.

### e2e

```bash
cd frontend
PUBLIC_API_BASE= corepack pnpm test:e2e               # every app; :admin, :console, :workspace, :demo for one
```

- **console:** its flows on the mock API: signing in and out, an agent, pausing every agent, a demo request becoming a
  client step by step, an invitation, a client, an SKU's gates, the Overview, Sign in's states and Agents at work, an
  unknown client and page.
- **workspace:** the journey on the stub, each person's move made in the real screens: Priya, Rakesh bhai by phone (a
  wrong code first), a first-time invitee joining, a kirana's Not this time, Agrawal ji's bid and counter, switching
  person, the shell's back and forward, and resetting the demo data.
- **admin:** smoke runs only; the landing page's sections, menus, sheets, film and loader are covered by its a11y
  suite's specs.
- **demo:** the guided demo along the whole route (the console, the chips, the Mango Drink, the slow week), each
  person's move made inside the devices, the map, Back, the end, autoplay and the address.
- **Smoke** runs of every app in Firefox (desktop) and WebKit (tablet and phone).

One spec or project on an existing build:

```bash
cd frontend
corepack pnpm build:console
corepack pnpm --filter @smart-clearance/console exec playwright test --project=flows
```

### Parity

```bash
cd frontend
PUBLIC_API_BASE= corepack pnpm test:parity            # every app; :admin, :console, :workspace, :demo for one
```

Each app's build against its design3 prototype, pixel by pixel (pixelmatch), in the five projects: the landing page's
sections, every console screen, the workspace app's screens at each stage, and the guided demo's route map, stations,
map and end. The threshold is 0.3% of the pixels (0.5% for the workspace app). A failure writes the two shots and the
difference beside the report.

## The live tests

### Live e2e: the landing page and the console on the real API

```bash
backend-api/scripts/e2e.sh
```

Needs backend-api running (`backend-api/scripts/dev.sh`) and the apps' `.env.local` pointing at it
(`backend-api/scripts/app-env.sh`); it starts the frontend's dev servers if they aren't running. Through Firebase
Authentication: Book a demo on the landing page, a wrong then a right sign-in, the New client flow from that request,
an agent, an invitation, the plan, an SKU's gates, the Overview, Agents at work moving after `hydrate.sh --tick`, the
audit log in the signed-in name, and Support refused a plan change. The default password reaches the test process from
Secret Manager and is never printed. It adds a client to the local database (`hydrate.sh --reset` rebuilds it).

### The journey walk, over HTTP

```bash
backend-api/scripts/walk.sh                          # the whole journey, both batches
backend-api/scripts/walk.sh --day-minutes 60 --until detect
```

Munchly's journey walked by each person's API calls (no browser), signed in with Firebase custom tokens, while the
agents' worker answers through Pub/Sub, BigQuery and Cloud Storage. Use it to bring a journey to a stop before a
journey suite or a demo (`--until setup|detect|photo|plan|approve|orders|deal|donation|settle|papers`), or to check
the back end alone. `--api … --origin https://munchly-smartclearance.web.app --allow-env prod` walks production, on the
maintainer's yes only.

## The journey suites

Recorded browser runs of Munchly's **live** journeys (`frontend/workspace/tests/journey/`): from the console's Reset
journey to Impact's report, every person acting in the real UI in turn (Neha in the console, Priya, the distributor,
each kirana, the ExpireSoon buyer, the food bank), one page driving everyone so a run is one recording. Each checks the
story's figures as it goes, softly, so the run reaches the end and reports every finding.

### Before a run, locally

On production none of this is needed: see [On production, from your own machine](#on-production-from-your-own-machine).

1. backend-api on :8000 (`backend-api/scripts/dev.sh`), on a world with Munchly's live workspace
   (`backend-api/scripts/hydrate.sh --reset`, or `--live-only` on a world that already has its story).
2. The agents' pull worker: `agents/scripts/dev.sh` (live Gemini), or `MODEL_TIER=stub agents/scripts/dev.sh` to
   replay recordings. Make sure no older worker from another checkout is running: it shares the local subscriptions and
   takes events.
3. The workspace app's and the console's dev servers on :5175 and :5174 (`cd frontend && corepack pnpm dev:workspace`,
   `corepack pnpm dev:console`), their `.env.local` pointing at the API (`backend-api/scripts/app-env.sh`). The
   Firebase browser keys accept only those origins.
4. For the PDFs: Pango (`brew install pango` on a Mac).

People sign in with Firebase custom tokens (`backend-api/scripts/sessions.sh`); no password is typed or printed.

### Options

```bash
E2E_SLOWMO=120 corepack pnpm test:journey --headed        # watch it in a browser window
corepack pnpm test:journey --ui                           # Playwright's UI mode, step by step
E2E_FROM=deal E2E_UNTIL=truck corepack pnpm test:journey  # part of it, on the journey as it stands
E2E_LEFTOVER=3 corepack pnpm test:journey:leftover        # fewer kiranas sit out
E2E_TARGET=prod corepack pnpm test:journey                # on production (SC-137): the deployed apps, Cloud Run
```

- `E2E_DAY_MINUTES`: the journey day the reset starts (60 by default; 1440, 60, 5 or 1). At 5 or 1 the kiranas'
  48-hour window can close before every shop has ordered.
- `E2E_SETTLE`: how long each screen is held before its still (1200 ms).
- `E2E_TARGET=prod` needs nothing local running; the apps' production settings are read from the repository's
  variables with `gh`. It resets production's journey and calls production's Gemini: on the maintainer's yes only.

### After a run

- **Set Munchly's journey day back to 24 hours.** The suites leave it at the reset's 60 minutes:

  ```bash
  backend-api/scripts/hydrate.sh --day-minutes munchly=1440
  ```

- **Read the report.** Each run writes `report.md` and `report.json` (the steps, the figures against the story's, the
  findings: page errors, failed API calls, figures off the story, any NaN, `undefined` or Invalid Date on screen), a
  still for each step and the recording, under `test-results/journey/`. Runs worth keeping are copied, with their
  report, into `frontend/workspace/tests/journey/runs/<date>/`; the recordings stay local.

### On production, from your own machine

> [!IMPORTANT]
> **This runs on production.** The Mango and Chips suites start Munchly's live journey again and call live Gemini; the
> full admin and console suite adds a new client each run; the walkthrough and the tour change two agent settings.
> Run them on the maintainer's yes only, and set the journey day back to 24 hours afterwards (step 8).

The journey suites can run against the deployed apps instead of a local stack:
- the landing page, [smartclearance.web.app](https://smartclearance.web.app);
- the console, [smartclearance-console.web.app](https://smartclearance-console.web.app);
- Munchly's workspace, [munchly-smartclearance.web.app](https://munchly-smartclearance.web.app);
- backend-api and the agents on Cloud Run, with live Gemini.

Nothing runs locally but Playwright. **They run live in your own browser:** Playwright opens Chromium on your machine
and drives the real apps, clicking, typing and signing people in, while you watch. The three-screen and admin suites
lay their screens out on a stage, show it in a window as they go, and record it as one video.

#### Where they are

All of them live in `frontend/workspace/tests/journey/`, one Playwright project each in
`frontend/workspace/playwright.journey.config.ts`, and run from `frontend/`:

| Journey | Suite | File | Command |
| --- | --- | --- | --- |
| Happy path, the Mango Drink on three screens (recorded) | Munchly Mango E2E on three screens | `munchly-mango-stage.journey.ts` | `corepack pnpm test:journey:mango-stage` |
| Happy path, the Masala Chips | Munchly Chips E2E | `munchly-chips.journey.ts` | `corepack pnpm test:journey` |
| Sad path, the Masala Chips destroyed at the godown, on three screens (recorded) | Munchly Chips Sad Path E2E | `munchly-chips-sad.journey.ts` | `corepack pnpm test:journey:sad` |
| Admin and console, in full (recorded) | Admin and console E2E | `admin-console.journey.ts` | `corepack pnpm test:journey:admin` |
| Admin and console, in a few minutes (recorded) | Admin and console walkthrough | `admin-console-walk.journey.ts` | `corepack pnpm test:journey:admin-walk` |
| Admin and console, in a minute (recorded) | Admin and console tour | `admin-console-tour.journey.ts` | `corepack pnpm test:journey:admin-tour` |

The helpers they share are beside them: `auth.ts` signs people in, `stage.ts` draws and records the screens, and
`flow.ts`, `read.ts`, `mango.ts`, `chips.ts` and `ledger.ts` hold the steps. The suites' own README
(`frontend/workspace/tests/journey/README.md`) has every step of each, and `runs/` keeps the reports of earlier runs.

#### What to install

On macOS or Linux, once:

| Tool | Why | Install |
| --- | --- | --- |
| Git | to clone the repository | `brew install git` |
| Node.js 22.17 or later, with corepack | Playwright and the suites | `brew install node`, then `corepack enable` |
| Playwright's Chromium | the browser the suites drive | `corepack pnpm --filter @smart-clearance/workspace exec playwright install chromium` (after `corepack pnpm install`) |
| ffmpeg | records the three-screen and admin suites' video | `brew install ffmpeg` |
| GitHub CLI (`gh`) | reads production's public settings (each app's API address and Firebase browser key) from the repository's variables | `brew install gh`, then `gh auth login` |
| Google Cloud CLI | signs the journey's people in, through `backend-api/scripts/sessions.sh` | `brew install --cask google-cloud-sdk` |
| uv | runs `sessions.sh` (it fetches its own Python) | `brew install uv` |

**And access:**

- **GitHub:** an account that can read `aibuilder2026/smart-clearance`'s Actions variables.
- **Google Cloud:** a Google account in Terraform's `operators` list (`infra/prod/terraform.tfvars`), which may act as
  `sc-api-local`. `sessions.sh` uses it to mint a Firebase custom token for each person, so no password is ever typed,
  stored or printed. Ask the maintainer to add yours and apply.

Pango, Docker, the local database and the dev servers are not needed for a production run.

#### Running one, step by step

1. **Get the code and its packages:**

   ```bash
   git clone https://github.com/aibuilder2026/smart-clearance.git
   ```

   ```bash
   cd smart-clearance/frontend && corepack pnpm install
   ```

   ```bash
   corepack pnpm --filter @smart-clearance/workspace exec playwright install chromium
   ```

2. **Sign in to GitHub and Google Cloud:**

   ```bash
   gh auth login
   ```

   ```bash
   gcloud auth login && gcloud auth application-default login
   ```

3. **Check you can mint a session.** This should print Neha's details as JSON (keep it out of logs):

   ```bash
   ../backend-api/scripts/sessions.sh neha > /dev/null && echo ok
   ```

4. **Check production answers:**

   ```bash
   curl -s "$(gh variable get PUBLIC_API_BASE --repo aibuilder2026/smart-clearance)/readyz"
   ```

   It should print `{"ok":true}`. The first call after a quiet spell can take a few seconds, while Cloud Run starts.

5. **Run a suite**, from `frontend/`, with `E2E_TARGET=prod`. `E2E_KEEP` copies the video where you name it, and
   `{stamp}` becomes the run's start time:

   The happy path, the Mango Drink on three screens (about 15 minutes; resets the journey):

   ```bash
   E2E_TARGET=prod E2E_KEEP='../../playwright-automation-videos/munchly-mango-e2e-prod-{stamp}.mp4' corepack pnpm test:journey:mango-stage
   ```

   The happy path, the Masala Chips (about 10 minutes; resets the journey; add `--headed` to watch it):

   ```bash
   E2E_TARGET=prod corepack pnpm test:journey --headed
   ```

   The sad path, the Masala Chips destroyed at the godown on three screens (about 18 minutes; resets the journey):

   ```bash
   E2E_TARGET=prod E2E_KEEP='../../playwright-automation-videos/munchly-chips-sad-e2e-prod-{stamp}.mp4' corepack pnpm test:journey:sad
   ```

   The admin and console in full (about 20 minutes; sets up a new client). This suite does not fill in `{stamp}`, so
   name the file yourself:

   ```bash
   E2E_TARGET=prod E2E_KEEP="../../playwright-automation-videos/admin-console-e2e-prod-$(date +%F_%H-%M-%S).mp4" corepack pnpm test:journey:admin
   ```

   The admin and console in a few minutes (adds no client; saves two agent settings on Kaveri Foods):

   ```bash
   E2E_TARGET=prod E2E_KEEP='../../playwright-automation-videos/admin-console-walk-prod-{stamp}.mp4' corepack pnpm test:journey:admin-walk
   ```

6. **Watch it.** The recorded suites open a window titled for the run, "Google Chrome for Testing", at the top left of
   your screen, showing every screen as it is recorded. If it opened behind other windows, bring it forward with
   Cmd+Tab. The recording is made from the stage, not the window, so moving or covering the window does not spoil it.
   `E2E_LIVE=0` runs with no window. The other suites run unseen unless given `--headed`.

7. **Read the result.** The terminal says passed or failed. Each run writes `report.md` (every step and its time, the
   figures against the plan, any findings), a still for each step and the recording, under
   `frontend/workspace/test-results/journey/`.

8. **Set production's journey day back to 24 hours.** `hydrate.sh --day-minutes` sets only the local database's, so
   do it in the console: sign in as staff, open Clients, then Munchly Foods, press the journey-day badge, and choose
   Real time.

#### What a production run changes

- **The Mango and Chips suites start Munchly's journey again** on production. Each person acts as themselves in the
  real apps, live Gemini is called (about GBP 0.05 to 0.10 a run), and the journey is left where the run ends.
- **Admin and console E2E sets up a new client each run,** one of the suite's fictional companies (Chambal Snacks,
  Kaveri Foods and so on), with its demo request, people and audit lines. The console cannot delete a client.
- **The walkthrough and the tour change two agent settings** on Kaveri Foods (the Watcher's gate, moved between 60
  and 65 days, and the Negotiator on Act), each with its audit line. They read Munchly Foods' settings and leave them
  as they are.
- **Run them on the maintainer's yes only:** they change production's data and spend money.

## Which journeys to cover

| When | Run |
| --- | --- |
| A change to any screen, component or stub | the gates; then, when asked, the a11y suite on the apps that show it, and parity if it ports a design3 change |
| A change to the guided demo | the gates (they hold the story to design3); when asked, the demo's e2e (the whole route) and a11y |
| A change to the console | the gates; when asked, the console's e2e and a11y, and the live e2e if it touches the API |
| A change to backend-api's journey, the agents or the papers | the backend and agents gates, `live-fixtures.sh` then the frontend gate; when asked, Munchly Chips E2E (the happy path) |
| A change to the food bank, staff sale or a three-line plan | when asked, Munchly Mango E2E (continuing) or Munchly Mango Leftover E2E (from a reset) |

The full set of live journeys, in the order that leaves a usable state: **Chips Leftover** (resets), **Mango Leftover**

## The agents' evals

```bash
agents/scripts/eval.sh                         # every set
agents/scripts/eval.sh negotiator --split held-out
agents/scripts/eval-harvest.sh --days 14       # runs that fell back or were corrected, as candidate cases
```

Each case goes through its agent's writer as the pipeline calls it, is scored by deterministic checks and, for the
agents that write words, by a Gemini Pro judge on a 1-to-5 rubric. The sets: Vision (73 label photos), Data (25 export
layouts), the Valuer, the Router, the Lister, Outreach and the Negotiator (whose reserve must never leak). Each set's
pass marks go to its `summary.json`; each result to BigQuery's `smartclearance_local.agent_evals`. They cost money:
the estimate is printed first, and they run on request only. `agents/README.md` has the pass marks.

## Reporting a run

Report what ran and its counts, as CLAUDE.md's records do:

- **a11y:** N pass for each app, 0 WCAG findings and every core component it uses on screen, or which rule failed on
  which screen and viewport, and which components no scan reached;
- **e2e:** N pass, and which projects failed (Firefox in a sandbox is expected);
- **parity:** N pass, and the largest difference as a percentage, with its page and viewport;
- **journey:** passed or not, the time and steps, the figures against the story's, and the findings from `report.md`;
- **evals:** each set's score against its marks, and what the run cost.

## When something gets in the way

- **A suite will not start:** a preview server is on its port. Stop it, or let the suite's own server take the port.
- **A dev server shows errors after a branch switch or a merge:** restart it, then reload the page.
- **A journey stalls at an agent's step:** check `agents/scripts/dev.sh` is running and is this checkout's (another
  checkout's worker takes the events and may run older code).
- **Papers without PDFs:** install Pango, restart the worker, then `backend-api/scripts/hydrate.sh --papers munchly`.
- **The local API hangs on a reload** while a workspace page holds its event stream open: restart `dev.sh`.
