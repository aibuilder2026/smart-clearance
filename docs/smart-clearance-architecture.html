Smart‑Clearance

Google AI Hackathon 2026 · Retail & Commerce · Technical architecture

Every near-expiry carton gets a second chance, routed by agents on Google Cloud.

Smart-Clearance finds an FMCG brand's stock that will not sell before its date, reads the carton's label, prices every way out, and waits for one person's yes. Then agents list the lot, offer it to kiranas, answer buyers, draft the GST papers and post the impact ledger. This page shows how it is built: Firebase at the edge, Cloud Run for the API and the agents, Gemini on Vertex AI for the words, Pub/Sub for the events, Cloud SQL as the system of record and BigQuery for the analytics.

The system

One picture of everything that runs

Static apps on Firebase Hosting call one API on Cloud Run. The API is the only writer: every change commits in one transaction with its audit line and its outgoing events, then Pub/Sub carries the events to a stateless agents service that asks Gemini for words and reports back. Pushes reach phones through Firebase Cloud Messaging; screens move on over a live stream.

What the brief asks about

Firebase, Cloud Run and Gemini, and why Firestore is not here

Each Google product was picked for a job the product has to do. Where one would have been a poor fit, we said so and used the one that fits.

Firebase

Hosting, Authentication, Cloud Messaging, web apps

  • Hosting serves each SvelteKit app as a static build on its own site: the prerendered landing page, the staff console, Munchly's workspace PWA and the guided demo. Deep links rewrite to the app, hashed assets cache as immutable, and the private apps send noindex, frame-denial and referrer headers.
  • Authentication (Identity Platform) signs everyone in with email and password from one user pool. Sign-up is off, so only backend-api creates accounts; a password policy and email-enumeration protection are on. The API verifies each ID token with firebase-admin.
  • Cloud Messaging carries the Notifier's pushes to members' phones and browsers through the PWA's service worker, so a distributor hears about a label photo request and an approver about a plan waiting.
  • Web apps and restricted keys: each app has its Firebase web app config, written by Terraform, and a browser key limited to the identity APIs from that app's own origins.

WhyThe apps are static over an API, so the whole frontend lives on Google's CDN with no server to run, and identity and push come from the same project with no password store or push service of our own.

Cloud Run

Two services, two jobs

  • backend-api, FastAPI on Python, is the public API and the system's only writer. It serves the REST routes, the live stream, the agents' /internal routes and the tick.
  • agents, Google ADK on Python, takes internal traffic only. Cloud Run's IAM lets in one identity, sc-invoker, which Pub/Sub's push subscriptions sign as.
  • Jobs on the same image: backend-api-migrate runs Alembic as the schema owner, and backend-api-hydrate builds a synthetic world through the services. Cloud Build runs the migration before every deploy.
  • Each runs as its own service account with an IAM database login, writes JSON logs that carry the trace, scales to zero, and rolls out one revision at a time behind a readiness check.

WhyContainers without servers: the same image runs on a laptop and in the cloud, service-to-service calls are signed with OIDC instead of shared secrets, and a quiet prototype costs next to nothing.

Gemini on Vertex AI

Two tiers, through the Agent Development Kit

  • Gemini Pro (gemini-3.1-pro-preview) writes where judgement shows: the Valuer's note on each exit, the Router's explanation of the split, the Negotiator's reply to a bid, and the evals' judge.
  • Gemini Flash (gemini-3.8-flash) reads and drafts: Vision reads the printed label from a distributor's photo, the Data agent maps an unfamiliar DMS export, and the Lister, Outreach (offers in Hindi, English and Marathi), Paperwork and Impact write their copy.
  • Called through google-genai on Vertex AI's global endpoint with the service account's own credentials: no API key exists. Every call asks for structured output against a schema.
  • Gemini supplies words only. backend-api computes every rupee, the words are checked against those figures, and a template stands in for any reply that fails.

WhyA multimodal model reads a crumpled carton label as printed, writes fluent shop offers in Indian languages, and runs under the project's own IAM, quotas and audit logs.

Firestore Not used, by design

Cloud SQL for PostgreSQL holds the record instead

  • The workspace is a ledger: money worked out by one set of rules, papers numbered in series, credit notes per line, and an audit log nobody may edit. That needs transactions across tables, constraints, triggers and SQL.
  • Live updates, the usual reason to reach for Firestore, come from PostgreSQL itself: a change NOTIFYs as it commits, and members read it as server-sent events, cut to their role on the server.
  • Events leave only after commit: each change writes its Pub/Sub messages to an outbox in the same transaction, so an agent never acts on a change that rolled back.
  • The same PostgreSQL runs on a laptop in Docker, so every test runs against a real database, never a mock.

WhyFirebase does what it is best at here (hosting, sign-in and push), and the record lives where transactions, joins and an append-only audit log come built in.

Every Google Cloud component

What each service does here, and why we chose it

All of it lives in one Google Cloud project, written in Terraform. Nothing is made by hand in a console, and no service account has a key.

Edge and identityWhere people meet the product
Firebase Hosting

A site per app, released by firebase-tools: the landing page prerendered with its data, and the console, workspace and demo as single-page apps with deep-link rewrites and immutable caching for hashed assets.

Static builds on a global CDN, each app with its own address, release and rollback.

Firebase Authentication

Identity Platform with email and password only, sign-up disabled, a password policy and email-enumeration protection. backend-api verifies ID tokens and makes accounts under a custom role limited to user management.

Managed sign-in with standard ID tokens, and no password store of our own.

Firebase Cloud Messaging

The Notifier sends each notification to the member's registered devices through the workspace PWA's service worker. backend-api holds a custom role that may only send messages.

One push channel for Android, installed iOS web apps and desktop browsers.

ComputeContainers, no servers
Cloud Run services

backend-api takes public traffic from the apps. agents takes internal traffic only, and only from sc-invoker, the identity Pub/Sub signs its pushes with.

Scale to zero, a revision per release, service-to-service auth with OIDC tokens.

Cloud Run jobs

backend-api-migrate runs Alembic as the schema owner's IAM login; backend-api-hydrate builds the synthetic world through the services. Both use the API's image.

One-off work with the same image and identity model, and no bastion host.

IntelligenceGemini writes; the rules decide
Vertex AI, Gemini

Pro for the Valuer, Router, Negotiator's bids and the evals' judge; Flash for Vision's multimodal label read, the Data agent's column mapping, the Lister, Outreach, Paperwork and Impact. Global endpoint, structured output, retries with backoff on quota and server errors.

Multimodal reading, Indian-language copy, and enterprise IAM and quotas in the same project.

Agent Development Kit

Each event runs one pipeline: SequentialAgent where a step needs the last one's result, ParallelAgent where it does not, LlmAgent with an output_schema for each model call, and custom steps for the deterministic work.

Google's framework for Gemini agents: composable, traced, and testable on recorded responses.

Events and timeDecoupling a tap from the work
Pub/Sub

Topics per environment for the agents' events and the Notifier, ordered by batch, with dead-letter topics. Production pushes to Cloud Run with an OIDC token; a laptop pulls the local subscriptions. Each message carries its traceparent.

At-least-once delivery with retries, ordering that keeps a batch's steps in sequence, and the same code locally with no emulator.

Cloud Scheduler

The journey's clock: sc-tick calls backend-api's tick every minute with an OIDC token. It runs the daily agents on the journey's own time, fires due timers, re-sends stalled events and flushes the outbox.

A managed clock with the same keyless auth, so a compressed demo day and a real one run on one mechanism.

DataRecord, analytics, files
Cloud SQL for PostgreSQL 18

The system of record: clients, members, batches, cases, papers, the ledger and the audit log. IAM logins only, through the connector, over TLS; the app's login has data access only, the audit log refuses edits by trigger; backups and point-in-time recovery.

A ledger needs transactions and constraints, and LISTEN/NOTIFY gives the live stream for free.

BigQuery

The agents' analytics: stock snapshots and secondary sales loaded from DMS exports, channel prices, the impact ledger, one row per agent run (model, latency, fallback, trace), and the evals' results.

Sell-through across distributors and pincodes is an analytical query; load jobs never load a file twice.

Cloud Storage

Buckets for label photos, DMS exports and Paperwork's PDFs, per environment. Phones upload straight to short-lived signed URLs, and papers open through signed links. Build sources and Terraform state live here too.

Files never pass through the API, and lifecycle rules tidy what is no longer needed.

TrustNo keys, no secrets in files
Secret Manager

The few secrets there are, such as the default password new accounts start on. Scripts generate them and pipe them in on stdin; services read them by reference at runtime.

Nothing secret in a file, a command line, a log, Terraform state or git.

IAM and service accounts

An account per job: the API, the agents, the migrator, the invoker, the builder and two CI deployers. Developers impersonate a local account in code from their own credentials. Custom roles for user management and messaging.

Least privilege, and every action in the audit logs under the identity that did it.

Workload Identity Federation

GitHub Actions trades its OIDC token for short-lived Google credentials, accepted only from this repository's ids and the protected prod environment, which only main may deploy to.

CI deploys with no stored credential at all.

DeliveryFrom a merge to a revision
Cloud Build

Builds each image with the last one's layers as cache, pushes it, runs the migration job on it, deploys the service and checks it answers ready. CI starts it as sc-builder, an account that may do only that.

Builds run inside Google's network, next to the registry and Cloud Run.

Artifact Registry

A private Docker repository for the API's and the agents' images, each tagged with its commit, with a cleanup policy. Cloud Build owns the images; Terraform ignores them.

In-region, private, and every running revision traceable to a commit.

OperationsSeeing a request end to end
Cloud Logging and Error Reporting

Every service writes one JSON object a line with severity, source and the request's trace, so Logs Explorer groups a request's lines and Error Reporting groups stack traces.

One place to read a request, from either service.

Cloud Trace, Telemetry API

OpenTelemetry spans over OTLP: each route, SQL statement and token check in the API, and each ADK agent, Gemini call and BigQuery job in the agents, all under the trace the browser started.

Google's recommended route into Cloud Trace, joined to Cloud Run's own sampled requests.

Cloud Monitoring and budgets

An uptime check on the API's readiness, alert policies for downtime, errors, latency, the database, dead letters, agent errors and fallbacks and push failures, log-based metrics, a dashboard and a billing budget.

Alerts reach the operator by email before a person notices.

The agents

Ten agents along nine stops, and one person's yes

A batch at risk moves through the same stops every time. Agents do the reading, the writing and the chasing; backend-api does the arithmetic; and nothing leaves the godown until the approver says yes.

Figures are computed, never generated

backend-api works out every price, split, credit note and ledger line by one set of money rules. The agents read previews of those figures and write words around them.

The reserve never reaches a prompt

The lowest price a buyer may get is cut from every case and preview an agent reads, and tests try hostile buyer messages to prove it.

A buyer's words are data

Messages go into the Negotiator's prompt between delimiters they cannot forge, as quoted text, never as instructions.

Every word is checked

Each figure in the copy must be one of the computed ones, a reply to a bid states the decided price and nothing else, and offers keep their shop placeholder and push length.

Structured output Gemini can fill

Every schema field is required, with null meaning absent, and no schema holds a free-keyed map, after the first live eval run showed how those come back.

Bounded calls

Each model call has a deadline, retries quota and server errors with backoff, and counts against a per-run budget; past it, the template stands in.

CI/CD

GitHub Actions gates every change; Cloud Build ships it to Cloud Run

A pull request runs five gates in parallel and builds the apps once. A merge to main signs in to Google with Workload Identity Federation, has Cloud Build build, migrate and deploy backend-api and then the agents, and releases the apps' build to Firebase Hosting.

Path-aware

A merge rebuilds backend-api only when backend-api/ changed and the agents only when agents/ changed; the apps release on every merge that touches the frontend, the designs or the infrastructure.

Migrate before deploy

Cloud Build runs the migration job on the new image before the service moves to it, so the schema is always ahead of the code reading it.

Ordered releases

backend-api deploys first, then the agents that call it, then the apps that read it, because the landing page prerenders against the live API.

Images owned by the build

Cloud Build tags each image with its commit; Terraform owns the service's configuration and ignores the image, so neither undoes the other.

Testing

Proven at every layer, from a pixel to a live Gemini reply

Fast gates run on every pull request. The browser suites (accessibility, end to end, parity, live and journey) and the live-model evals run when we ask for them, on a real machine, against real builds and real services.

GatesEvery pull request

Vitest · pytest · ruff · ESLint · svelte-check · gitleaks

  • Frontend: unit tests, drift tests that hold ported CSS to the design, golden texts of every role's screens, seed and icon checks.
  • Backend: pytest on a real PostgreSQL service container, the live journey walked over HTTP with in-memory Pub/Sub, Storage and Cloud Messaging.
  • Agents: every pipeline on recorded Gemini responses, its exact requests, its fallbacks, and the reserve never reaching a model.
  • Contracts: the money rules exist in JavaScript, TypeScript and Python, and shared fixtures hold all three to the same answers.
AccessibilityOn request

Playwright · @axe-core/playwright · WCAG 2.2 AA

Each app's production build, scanned in desktop, tablet and phone viewports, light and dark, with zero violations. Keyboard specs cover focus in sheets and alerts, the menu-button pattern and sign-in by keyboard; a motion spec fails any endless animation. A coverage check fails the run if an app uses a design-system component that no scan had on screen.

End to endOn request

Playwright · Chromium · Firefox · WebKit

The console's flows, the workspace journey on its stub, and the guided demo played beat by beat, on each app's build. Smoke runs in Firefox and in WebKit on iPad and iPhone profiles.

ParityOn request

Playwright · pixelmatch

Each app's build is compared with its approved design3 prototype, pixel by pixel, at desktop, tablet and phone sizes in both themes. The port cannot drift from the design that was signed off.

LiveOn request

Vitest + jsdom · Playwright · Firebase Auth

The workspace's live tests draw its screens on what backend-api actually answered at moments of the journey, recorded from the running API. The live end-to-end suite drives the landing page and the console against the real API and real Firebase sign-in, and reads each change back from the audit log under its own trace.

JourneyOn request

Playwright · Firebase custom tokens · live Gemini

Munchly Chips, Munchly Mango and their leftover variants. From a console reset to the impact report, every person acts in the real UI in turn: the operator, the distributor, each ordering kirana, the buyer and the food bank, with the agents on live Gemini. Sign-in uses custom tokens minted by an impersonated service account, so no password is handled. Each run records a video, a still per step and a report of findings, against the local stack or production.

EvalsOn request

live Gemini · deterministic scorers · Gemini Pro judge

Every agent's eval set runs through the same writer the pipeline calls: label photos rendered with blur, glare and tape for Vision, odd DMS headers for the Data agent, hostile buyer messages for the Negotiator. Scorers check the hard rules, a judge scores the words on a rubric, and results land in BigQuery.

Observability

One trace, from a tap to an agent's report

The apps send a traceparent with every call. Cloud Run keeps it, backend-api continues it into its spans, log lines and audit rows, and the outbox hands it to Pub/Sub, so the agents' run and its Gemini calls land in the same trace.

Logs carry the trace

Every JSON line written during a request names its trace and span, so Logs Explorer shows it under Cloud Run's own request line.

Audit rows carry the trace

Each change's audit row keeps the trace of the request that made it, so a line in the console leads back to its request.

Agent runs carry the trace

Each run's report and its BigQuery row hold its trace id, with model, latency and whether it fell back.

Sampled where it counts

A request Cloud Run sampled is always kept, a share of the rest is sampled, and every request keeps its trace id in its logs regardless.
