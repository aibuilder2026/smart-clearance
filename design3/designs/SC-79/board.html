The console: a client's runs on demand, and its journey from the start

SC-79 · console.smartclearance.com · three options for firing a client's scheduled runs and journey timers at once, and for starting its journey again, each built on the console itself. Munchly's journey is held still at day 1, Sat 3 Oct 10:15, in real time. Every company, person and figure is fictional.

The maintainer's request (8 Oct), with the answers to two questions:

  • “All batch runs should have a trigger which I should be able to control and do instant trigger from console screen against each agent for that client.”
  • “On console there should a button which will do the reset of journey at each client level.”
  • Control: keep the schedule as it is, and add triggers. Which: the scheduled runs (the Data agent's 08:30, the Watcher's 09:00) and the journey's timers (the offer window closing, the day-7 shelf check, the report due). Agents that answer an event keep running on their own.

The console now

Each agent's inspector has Run now, but it does something only for the Data agent and the Watcher, and the timers have no control at all. A journey starts again only from a terminal (hydrate.sh --journey-reset) or a paused Scheduler job.

What all three share

What can be fired

  • The Data agent's daily load and the Watcher's daily check.
  • The journey's pending timers: the offer window closing, the day-7 shelf check and the report due, each for its batch.
  • Each says when it falls due in journey time, how long that is from now in real time, and its rhythm.

Firing one

  • At once, with no question: it runs as if its time had come, and the toast says what it did.
  • The schedule does not move: a daily run fired now still runs tomorrow at its time.
  • A timer that cannot fire yet says why, and its button is off: the shelf check waits for the van round, the report for the papers and the shelf check.
  • An audit line in the staff member's name: “Ran the Watcher agent's daily check now for Munchly Foods”.

Starting the journey again

  • Behind a confirmation: open batches close as reset, the story's batches start again on day 0 at 08:00, at the client's current day length. Nothing is deleted.
  • Only for roles that may configure clients, and audited.
  • Afterwards the coming runs are day 0's: the Data agent at 08:30 and the Watcher at 09:00.

Option A · On each agent

Recommended

The triggers hang under the agent they belong to, on the Agents tab's pipeline: the Data agent's daily load under Data, the Watcher's daily check under the Watcher, the offer window and the shelf check under Outreach, the report under Impact. The inspector lists the selected agent's own, or says what starts it. Reset journey… joins Pause every agent in the client's actions menu.

Where
The Agents tab, the client page's first tab: on each agent's stop, and in its inspector. The reset is in the actions menu (⋯) by the title.
Trade-offs
Matches the request's “against each agent”, and puts the trigger beside the schedule each stop already states. The Agents tab grows by five rows, and what comes next across agents is read top to bottom rather than in time order. The reset is one menu away, which suits a destructive action.
What the build touches
design3 console.jsx (AgentPipeline, AgentInspector, the actions menu, the alert) and core/platform.js (the schedule, firing, reset); the frontend's AgentsTab and client page; the contract's ConsoleApi.journey, fireTrigger, resetJourney; backend-api's console routes over the tick, the timers and journey/reset.py.

Option B · One journey sheet

SC-68's badge in the client's head becomes the journey's: Day 1 · Sat 3 Oct 10:15 · Real time, on every tab. It opens one sheet: the day and its length, everything coming up in time order with its button, and Start the journey again at the foot.

Where
The client page's head on every tab, and a sheet from the side (from the bottom on phones).
Trade-offs
Everything a demo needs in one place, in the order it will happen, from any tab. The triggers are not on the agents, so “against each agent” is read as a row per agent. The badge is longer than SC-68's and wraps on phones.
What the build touches
As A, with the badge and a sheet instead of the pipeline's rows and the menu item; SC-68's day-length sheet opens from the new sheet.

Option C · A Journey tab

A tab of its own after Agents: the day in journey time with its length, Coming up in time order with each button, Earlier with what has run, and Start the journey again set apart in red ink.

Where
A new eighth tab, /clients/<id>/journey.
Trade-offs
The most room, and the only option that shows what already ran beside what is coming, so a demo can be narrated from it. One more tab in a full row, and staff leave the Agents tab to fire a run.
What the build touches
As A, with a new tab and route instead of the pipeline's rows; the runs' history comes from the agent runs backend-api already records.

Recommended: A. It is the request in its own words, a trigger against each agent, and it puts each trigger beside the schedule the agent's stop already states, so nothing new has to be learned. It adds no tab and no sheet, and the reset sits with Pause every agent, the other client-wide action. B is the better stage for a presenter who wants everything in time order from any tab; C is the place to grow a demo's controls if there will be more of them.
